# Filters / Positioning tutorial pipeline (UWB TDoA)
[English](README.md) | Русский

Этот слой осуществляет трансформацию сырых данных от анкоров в финальную траекторию пользователя.

Идея простая: в базовой структуре проекта у нас уже был обработчик `sensor_fusion` для готовых координат. Здесь показано, как выглядит путь до этой точки, если мы начинаем с UWB-анкоров и TDoA.

Важно: это не production. Это набор модулей, который демонстрирует последовательность обработки, границы ответственности и места, куда потом вставляется продовая реализация.

## Входные данные и инфраструктура

Предполагается, что на площадке стоят анкоры (например, **UbiTrack-A1**), и что они уже умеют работать в сетке и участвовать в межанкорной синхронизации времени в рамках своей платформы. Для нас это означает практическое допущение: с анкоров приходят timestamps, которые можно привести к общей временной шкале (или они уже близки к ней).

То есть в этом проекте не реализуется низкоуровневая синхронизация на уровне firmware. А начинаем с момента, когда:

- anchor receptions уже доступны на Ubuntu/edge,
- у них есть `anchor_id`, `frame_id`, `tag_id`, `rx_time_s`,
- и есть хотя бы минимальные quality fields (RSSI / first-path / flags), если железо их отдаёт.

## Последовательность шагов

### 1. `anchor_sync_adapter.py`

Это не синхронизация анкоров как таковая, а адаптер допущений. Он хранит состояние по каждому анкору (насколько свежа синхронизация, какой quality score пришёл от нижнего слоя, можно ли временно исключить anchor из расчёта).

Зачем нужен: даже если синхронизация есть из коробки, в верхнем пайплайне полезно иметь явный слой, который умеет сказать: этот anchor сейчас не надо использовать.

### 2. `tdoa_builder.py`

Из сырых событий приёма (`AnchorReception`) собирает измерение TDoA для одного UWB frame/tag:

- группирует receptions по `(tag_id, frame_id)`,
- выбирает reference anchor,
- считает разности времён прихода,
- переводит их в разности расстояний (`Δr = c * Δt`).

На выходе — структурированное измерение, пригодное для multilateration.

### 3. `multilateration.py`

Решает обратную задачу: по набору TDoA (разностей расстояний до anchors) оценивает позицию `(x, y)`.

Реализация здесь — учебная weighted Gauss-Newton. Она показывает:

- как формируется residual,
- как использовать prior (предсказание трекера) как стартовую точку,
- как использовать веса измерений,
- как получить грубую оценку covariance/residual score.

### 4. `quality_filters.py`

Это слой валидации:

- отбрасывает явно плохие receptions,
- помечает вероятный NLOS по простым эвристикам,
- делает gating по скорости / Mahalanobis distance относительно предсказанного состояния.

В production этот слой обычно растёт сильнее всего. Здесь он специально простой, но показывает правильное место в архитектуре.

### 5. `kf_core.py`

Общий линейный Kalman core (`predict` / `update`) без знания про UWB, IMU и спорт. Его используют и учебный `kalman_tracker.py`, и верхний модуль `tracking_mvp/sensor_fusion.py`, чтобы не дублировать математику.

### 6. `kalman_tracker.py`

Базовый CV (constant velocity) Kalman tracker для 2D:

- принимает измерения позиции после multilateration,
- умеет predict/update,
- поддерживает covariance измерения,
- работает как stateful streaming-компонент.

Это уже слой траектории, а не локализации из радио.

### 7. `imm_tracker.py`

Учебный IMM поверх нескольких Kalman-моделей.

Здесь он специально сделан максимально прозрачным: несколько фильтров с различной интенсивностью шума процесса (process noise), байесовское обновление вероятностей моделей и смешивание состояний.

## Как это связано с нашим текущим scaffold

Поток теперь можно мыслить так:

`anchor RX -> sync adapter -> TDoA builder -> multilateration -> quality filters -> Kalman/IMM -> analytics`


## Что обязательно усилить перед реальным использованием

В этой папке специально оставлены упрощения:

- 2D модель, без детальной высоты и геометрии тела/тега,
- простые NLOS эвристики вместо полноценного quality model,
- упрощённая covariance оценка,
- минимальный IMM без продвинутых motion modes,
- нет ассоциации нескольких тегов (multi-target tracking).

Но как инженерная база это уже хороший шаг: код можно читать, запускать на синтетике и заменять модули по одному.
